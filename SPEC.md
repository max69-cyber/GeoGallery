> Статус: **черновик v0.8**, 2026-11-05.
> Этот файл отвечает на вопрос **«что строим»**: продукт, данные, поведение, контракты.
> Вопросы **«как учиться и в каком порядке делать»** — в [`AGENTS.md`](AGENTS.md).

---

## 1. Суть проекта

**GeoGallery** — Android-приложение: фото снимаются встроенной камерой, каждый снимок автоматически
привязывается к месту на карте, а ИИ генерирует подпись по запросу. По сути это галерея, организованная
не по датам, а по местам.

- **Тип проекта:** учебный, для портфолио. Критерий успеха — качество кода и законченность,
  а не монетизация и не число установок.
- **Чему служит:** Clean Architecture + MVVM, камера, геолокация, карты, offline-first с синхронизацией,
  интеграция ИИ-API через собственный бэкенд.
- **Очерёдность:** сначала дорабатывается ReelTusky, затем начинается GeoGallery.
- **Публикация в магазин:** не планируется. Достаточно репозитория, README, скриншотов/GIF и демо-видео.
- **Описание для GitHub:** `android photo archive that pins every shot to a place on the map, on kotlin + compose`
- **Пакет / applicationId:** `com.rayxaus.geogallery`

## 2. Объём MVP

### Входит
| Область | Коротко |
|---|---|
| Гостевой режим | Приложение полностью работает без аккаунта; аккаунт нужен только для синхронизации и ИИ-подписей |
| Аккаунты | Необязательные: регистрация и вход (email + пароль), перенос локальных данных в аккаунт, выход, удаление аккаунта и данных |
| Съёмка | Встроенная камера (CameraX), только фото 4:3 (3:4 в портрете), координаты и время фиксируются в момент снимка |
| Места | Автоподбор места по радиусу или создание нового; переименование (в том числе сразу после создания) |
| Карта | Метки мест с превью и счётчиком, кластеризация, переход в галерею места |
| Фото | Экран всех фото (включая «Без места»), просмотр, удаление, ручная подпись |
| ИИ-подписи | Пользователь запрашивает подпись для выбранного фото. Бэкенд получает уменьшенную копию. Успешный ответ сразу сохраняется как подпись |
| Офлайн | Локальная БД — источник правды. WorkManager запускает синхронизацию архива при наличии сети |
| Приватность | Явное согласие на отправку фото в ИИ, отзыв согласия, удаление аккаунта |
| Состояния | Статусы синхронизации, пустые состояния и ошибки как явные требования (см. §13) |

### Не входит (версия 2+)
- Импорт из галереи устройства. Для привязки используется текущая геолокация телефона в момент импорта; геометка из файла игнорируется. Если замера нет, его точность неизвестна или погрешность больше 30 м, снимок сохраняется без места (§5.2).
- Видео.
- ИИ-группировка фото в альбомы и поездки, поиск по смыслу (эмбеддинги).
- Расшаривание архива с другими пользователями.
- Дубликаты и серии кадров.
- On-device теги (ML Kit) как офлайн-режим подписей.
- Ручная привязка фото к месту, слияние мест (в том числе дублей после переноса гостевых данных).
- Названия мест через reverse geocoding или ИИ-предложение.
- ИИ-теги и поиск по ним — возможное расширение после MVP.
- Несколько аккаунтов на одном устройстве одновременно.
- Подтверждение email.
- Kotlin Multiplatform (вынос `domain` в shared).

## 3. Пользовательские сценарии

| # | Сценарий | Ожидаемый результат |
|---|---|---|
| S0 | Без аккаунта | Всё, кроме синхронизации и ИИ, работает локально; аккаунт нигде не навязывается |
| S1 | Регистрация / вход | Необязательно; доступны из настроек и из sheet ИИ. Требуют сети. Сессия сохраняется между запусками. Если на устройстве есть гостевые данные — предложение перенести их в аккаунт (§5.1) |
| S2 | Первый запуск | Онбординг ведёт на карту. Камера и геолокация запрашивают доступ при первом действии, которому он нужен |
| S3 | Съёмка | Приложение сохраняет файл, время и доступные координаты. Если координаты получены, а погрешность неизвестна или больше 30 м, фото сохраняется без места и камера предлагает уточнить геолокацию (§5.2) |
| S4 | Карта | Метки мест (превью последнего фото + счётчик), кластеры при отдалении; тап по метке открывает место |
| S5 | Место | Сетка фото места, переименование места |
| S6 | Фото | Просмотр, подпись (с пометкой источника), редактирование подписи, удаление |
| S7 | ИИ-подпись | Пользователь нажимает «Сгенерировать подпись» на экране выбранного фото. Приложение при необходимости предлагает войти или дать согласие, затем выполняет явный запрос. Пока идёт запрос, ручное редактирование недоступно. Успешный ответ сразу заменяет текущую подпись. При ошибке доступен ручной повтор |
| S8 | Офлайн | Всё, кроме действий из §13 «Требует сети», работает без сети; с аккаунтом у фото виден статус синхронизации; при появлении сети всё уходит само |
| S9 | Выход | Если есть несинхронизированные данные — предупреждение до выхода. После выхода локальный архив очищается (данные остаются в аккаунте на сервере) |
| S10 | Удаление аккаунта | Подтверждение → удаляются данные на сервере, локальные данные и токены |

## 4. Экраны и навигация

| Экран | Назначение |
|---|---|
| Onboarding | Приветствие и переход на карту |
| **Map** (главный, стартовый) | Карта с метками мест, кнопка «моё местоположение», FAB камеры, переход к списку мест, всем фото и в настройки. Аккаунт для старта не нужен |
| Camera | Превью камеры, кнопка съёмки, подтверждение сохранения. Камера остаётся открытой для серии снимков. Для нового места доступно действие «Переименовать», а для координат, не прошедших проверку точности, — «Уточнить геолокацию» (§5.2) |
| Photos | Все фото сеткой по дате добавления (`createdAt`), включая фото без места (с пометкой); фильтр «Только без места». Единственный путь к фото без места — на карте их нет |
| Places | Список мест (обложка, название, число фото) — альтернативный вид к карте; работает и там, где карта недоступна (нет сети/тайлов) |
| Place | Сетка фото места, переименование |
| Photo | Полноэкранный просмотр, свайп между фото текущего списка (места или всех фото), подпись, «Сгенерировать подпись», дата, место, статус синхронизации |
| Auth | Вход / регистрация; открывается из Settings или из sheet ИИ |
| Settings | Аккаунт (войти / email + выйти / удалить), согласие на ИИ, сводка синхронизации («N ожидают, M с ошибкой» + «повторить») |

Модальные элементы: sheet согласия на ИИ (или предложения войти, §9), диалог переноса гостевых данных при входе (§5.1),
подтверждения выхода и удаления аккаунта.

```
Onboarding ──► Map
Map ──► Camera
 ├────► Place ──► Photo
 ├────► Places ─► Place
 ├────► Photos ─► Photo
 └────► Settings ──► Auth
Photo ── sheet ИИ ──► Auth (если нет аккаунта)
```

## 5. Функциональные требования

### 5.1 Аккаунты и гостевой режим
- **Аккаунт необязателен.** Без него приложение работает полностью локально («гостевой режим»);
  аккаунт добавляет синхронизацию с сервером и ИИ-подписи (ИИ идёт через бэкенд с лимитами на пользователя).
- **Одно устройство — один владелец данных в каждый момент.** Локальная БД принадлежит либо гостю,
  либо текущему аккаунту; id текущего аккаунта хранится в настройках, а не в каждой записи.
  Поэтому данные разных аккаунтов на устройстве не смешиваются и конфликтов между аккаунтами нет.
- Регистрация и вход по email + паролю; валидация формата — чистые функции в `domain`.
- **Вход при наличии гостевых данных:** диалог «Перенести N фото с этого устройства в аккаунт?»
  - «Перенести» — гостевые записи становятся данными аккаунта, получают `PENDING` и уходят на сервер;
    затем подтягиваются данные аккаунта (`/sync`). Конфликтов id нет — UUID генерируются на клиенте.
    Близкие места из гостевых данных и из аккаунта могут задублироваться — в MVP допускается (слияние мест — v2).
  - «Отмена» — вход не выполняется, гостевые данные остаются как есть.
- Токены access/refresh, автоматическое обновление; при невозможности обновить — синхронизация приостанавливается
  и предлагается войти заново тем же аккаунтом, **локальные данные не теряются**.
- **Выход:** если есть несинхронизированные данные — предупреждение («N фото ещё не на сервере и будут потеряны»).
  После подтверждения локальная БД, файлы и токены очищаются; приложение возвращается в гостевой режим с пустым архивом.
- **Удаление аккаунта** (требует сети): подтверждение → удаляются серверные данные, затем локальные данные и токены.

### 5.2 Съёмка
- CameraX, только фото. Превью и снимок используют формат 4:3 на телефонах и планшетах (3:4 при портретной ориентации). Файл хранится в app-specific хранилище (не в системной галерее).
- В момент снимка фиксируются `createdAt` и координаты (если доступны). Для будущего импорта `createdAt` — время импорта; исходная дата съёмки не используется. При скачивании сохраняется `createdAt` с сервера.
- Нет разрешения на геолокацию / GPS выключен / координаты не получены за таймаут → фото всё равно
  сохраняется, `location = null`, `placeId = null`, видно на экране «Все фото» с пометкой «Без места» (на карте его нет).
- Для автоподбора места нужна известная оценка погрешности не больше 30 м. Если координаты получены,
  а `accuracyMeters = null` или `accuracyMeters > 30`, фото сохраняется с измеренными координатами и `placeId = null`.
  На экране камеры появляется действие «Уточнить геолокацию» для этого снимка. По нажатию приложение запрашивает
  новый замер. Если повторный замер проходит ту же проверку точности, приложение обновляет координаты того же фото
  и запускает автоподбор места по §5.3. `createdAt` не меняется. При неудачном повторе фото остаётся без места.
- Ориентация снимка (EXIF-поворот) учитывается корректно.
- Оригинал хранится локально; для сети и ИИ формируются уменьшенные копии.
- **Снимок не должен теряться**: файл и запись в БД сохраняются до любых сетевых действий.

### 5.3 Места
- Привязка только автоматическая, ручной нет (v2).
- Правило подбора: ищем место, у которого расстояние от центра до точки снимка ≤ радиуса места.
  Если подходящих несколько — ближайшее по расстоянию до центра. Если нет — создаём новое
  с центром в точке снимка.
- Радиус нового места по умолчанию — **40 м** (константа в `domain`, стартовое значение для проверки на снимках).
- Центр места в MVP не сдвигается при добавлении фото.
- **Название по умолчанию** — «Новое место · дата первого снимка» (например, «Новое место · 19 окт»).
  Строка не хранится: UI собирает текст из `Place.createdAt` с учётом локали.
  Пользовательское название хранится в `name`; `name == null` значит «не переименовано».
- Переименовать можно сразу после создания (Snackbar на экране камеры) и в любой момент на экране места.
  ИИ-вариант названия — v2.
- Если из места удалено последнее фото и оно не переименовано пользователем — место удаляется
  (tombstone, как у фото); если переименовано — остаётся пустым. *Предварительно, см. §14.*

### 5.4 Карта
- Метка = место: миниатюра последнего фото + счётчик снимков.
- Кластеризация при отдалении; тап по кластеру приближает камеру карты.
- Начальная позиция камеры: текущая локация, иначе последнее место, иначе нейтральный вид по умолчанию.
- Тап по метке → экран Place. Кнопка «моё местоположение», FAB камеры.
- SDK карты — открытый вопрос (§14).

### 5.5 Фото
- Просмотр, подпись, дата/время, место, статус синхронизации.
- Ручное редактирование подписи → `CaptionSource.USER`.
- Удаление: локально сразу (с возможностью отмены через Snackbar, как в ReelTusky),
  на сервере — через синхронизацию (tombstone, см. §8).

### 5.6 ИИ-подписи
См. §9.

### 5.7 Настройки и приватность
- Переключатель «Разрешить отправку фото в ИИ» по умолчанию выключен. Отзыв согласия отменяет активный запрос на стороне клиента.
  Включается из настроек или из sheet согласия при первой попытке использовать ИИ (§9).
- Аккаунт: войти / зарегистрироваться (в гостевом режиме) или email + выйти + удалить аккаунт.
- Сводка синхронизации (только с аккаунтом).

## 6. Модель данных

Идентификаторы — **UUID `String`, генерируются на клиенте**: объекты можно создавать офлайн,
а синхронизация остаётся идемпотентной.
Время — `Instant` (UTC) в `domain`, epoch millis в Room, ISO-8601 в API; форматирование для показа — только в UI-слое.

### Domain-модели
| Модель | Поля |
|---|---|
| `Photo` | `id`, ссылка на локальный файл (без `android.net.Uri` в `domain`), `location: GeoPoint?`, `placeId: PlaceId?`, `caption: Caption?`, `syncStatus`, `createdAt`, `updatedAt`, `deletedAt?` (tombstone) |
| `Caption` | `text`, `source` (`AI` или `USER`) |
| `CaptionError` | `NO_NETWORK`, `LIMIT_REACHED`, `UNAVAILABLE` (ИИ выключен / 503), `REJECTED` (пустой ответ или отказ модели), `TIMEOUT`, `UNKNOWN` |
| `Place` | `id`, `name: String?` (`null` — не переименовано), `center: GeoPoint`, `radiusMeters`, `syncStatus`, `createdAt`, `updatedAt`, `deletedAt?` (tombstone). Число фото и обложка — производные |
| `GeoPoint` | `latitude`, `longitude`, `accuracyMeters?` |
| `User` | `id`, `email` |
| `SyncStatus` | `PENDING`, `SYNCED`, `FAILED`. В гостевом режиме все записи остаются `PENDING` и индикатор не показывается |

`GeoPoint.accuracyMeters` — оценка горизонтальной погрешности замера. `null` допустим для точки,
которую задали как координаты без замера, или для источника без оценки погрешности. Для успешного замера
через `LocationManager` значение заполнено. Если замера нет, `Photo.location = null`.


### Правила подписей
1. Пока запрос выполняется, ручное редактирование подписи этого фото и повторный запуск недоступны.
2. Успешный ответ сразу заменяет текущую подпись: текст сохраняется с источником `AI`. Подтверждение не требуется.
3. После завершения запроса ручное редактирование снова доступно. При сохранении правки источник меняется на `USER`.
4. При ошибке или отмене текущая подпись остаётся без изменений.

При сохранении подписи, сгенерированной ИИ или отредактированной вручную, обновляется `Photo.updatedAt`.

### Четыре вида моделей
| Слой | Класс | Для чего |
|---|---|---|
| Data (сеть) | `PhotoDto`, `PlaceDto` | Повторяет JSON API: имена полей, nullable, строки вместо enum, ISO-даты |
| Data (БД) | `PhotoEntity`, `PlaceEntity` | Структура таблиц Room: epoch millis, внешний ключ `placeId`, локальные поля (`syncStatus`, путь к файлу) |
| Domain | `Photo`, `Place` | Бизнес-модели без аннотаций и привязки к источнику |
| Presentation | `PhotoUi`, `PlaceUi` | Готово к показу: отформатированная дата, текст статуса, флаги для экрана |

Мапперы стоят на границах слоёв. Разделяем модели там, где они реально различаются, а не «на всякий случай».

## 7. Юзкейсы MVP

Юзкейс заводим, когда есть логика (правила, комбинирование источников). Простые чтения и записи,
которые только проксируют репозиторий, идут из ViewModel напрямую в репозиторий.

| Юзкейс | Что делает | Ключевые правила |
|---|---|---|
| `CapturePhoto` | Принимает снимок от `PhotoSource`, сохраняет `Photo` с учётом качества геолокации и планирует синхронизацию для аккаунта | Файл и запись в БД сохраняются до сетевых действий. Подбор места запускается для координат, прошедших проверку по §5.2 |
| `ResolvePlaceForLocation` | Подбор места по координатам или создание нового | Правило §5.3; ядро логики, тестируется на JVM |
| `DeletePhoto` | Tombstone + пересчёт места | Пустое неименованное место удаляется |
| `GenerateCaption` | По действию пользователя асинхронно запрашивает и сохраняет подпись выбранного фото | Требует аккаунта, согласия и сети. Пока запрос выполняется, повторный запуск и ручное редактирование подписи недоступны (§6) |
| `SignIn` / `SignUp` | Вход / регистрация с учётом гостевых данных | Если есть гостевые данные — требует решения о переносе; после входа запускает синхронизацию |
| `SignOut` | Выход | Предупреждает о несинхронизированных данных; очищает БД, файлы и токены |
| `DeleteAccount` | Удаление аккаунта и данных | Подтверждение, требует сети; сначала сервер, потом локальные данные |
| `SyncPending` | Отправка и получение изменений архива | Вызывается `SyncWorker` для текущего аккаунта |

Напрямую из репозитория: наблюдение за местами и фото, переименование места, ручная правка подписи
(валидация email и пароля — чистые функции в `domain`).
Состав уточняется по ходу: юзкейс появляется, когда во ViewModel возникает бизнес-логика.

## 8. Офлайн-first и синхронизация

- **Источник правды — Room.** UI наблюдает только БД (Flow), сеть пишет изменения в БД.
- **Синхронизация работает только при наличии аккаунта.** В гостевом режиме записи копятся как `PENDING`
  и уходят на сервер после входа с переносом данных (§5.1).
- Локальное изменение сначала сохраняется в Room со статусом `PENDING`. Для текущего аккаунта
  WorkManager планирует уникальную синхронизацию архива. Одновременно выполняется не более одного `SyncWorker` для архива.
- `SyncWorker` читает из Room и отправляет порциями ожидающие изменения фото и мест, включая записи с `deletedAt`.
  Новое место отправляется перед фото, которое на него ссылается. `syncStatus` обновляется для каждой записи отдельно.
  Изменения, сохранённые во время синхронизации, обрабатываются в текущем или следующем проходе.
- Для синхронизации нужны сеть и действующая сессия. Временные сбои повторяются с экспоненциальной задержкой,
  запросы идемпотентны по клиентскому UUID.
- Загрузка фото: метаданные и файл — одним запросом или двумя шагами (решается при проектировании бэкенда).
- При запуске приложения, после входа и периодически `SyncWorker` получает изменения через `GET /sync?since=<cursor>`.
  Изменения из ответа применяются одной транзакцией.
- Удаление — через tombstone (`deletedAt`) до подтверждения сервером, затем физическое удаление.
- Конфликты в MVP: last-write-wins по серверному `updatedAt`, включая подписи. Генерация по явному запросу пользователя считается изменением подписи (§6).
- Индикатор: статус у каждого фото, сводка в настройках, кнопка «повторить» для `FAILED`.

## 9. ИИ-подписи

- Провайдер спрятан за интерфейсом `CaptionGenerator` (`domain`). Реализация в MVP —
  `RemoteCaptionGenerator`, который ходит на наш бэкенд. Прямых вызовов провайдера из приложения нет,
  ключ хранится только на сервере.
- **Вход запроса:** уменьшенное JPEG (≈1000 px по длинной стороне, без EXIF), название места (если есть),
  дата и время суток добавления фото (`createdAt`), язык подписи. Точные координаты не отправляются.
- **Ответ:** `caption` (1–2 предложения). Структурированный JSON,
  который бэкенд валидирует перед отдачей.
- **Кэш:** по хэшу уменьшенного изображения и языку — одинаковый кадр не считается и не оплачивается дважды.
- **Лимиты:** число подписей в сутки и в месяц на пользователя, проверка на бэкенде (значения в конфиге).
- **Выключатель:** серверный флаг отключает ИИ глобально; приложение показывает «подписи временно
  недоступны», остальное работает.
- **Нужен аккаунт:** бэкенд считает лимиты на пользователя, поэтому в гостевом режиме ИИ недоступен.
- **Согласие:** копия для ИИ отправляется только после явного согласия. Согласие можно отозвать в настройках.
- **Запуск по запросу пользователя.** Действие «Сгенерировать подпись» на экране фото запускает запрос для этого фото, если пользователь вошёл и дал согласие. Если одного из условий нет, открывается `ModalBottomSheet`.
  - нет аккаунта → объяснение, что ИИ работает через аккаунт, кнопки «Войти» / «Не сейчас»;
  - есть аккаунт, нет согласия → что именно уходит (уменьшенная копия без EXIF и координат, название места, время),
    куда и что согласие можно отозвать в настройках. «Разрешить и запросить» даёт согласие и отправляет запрос для выбранного фото. «Не сейчас» закрывает окно.
  Согласие, выданное в настройках, разрешает будущие ручные запросы. После входа пользователь сам запрашивает подпись.
- **Выполнение.** Запрос выполняется асинхронно, пока приложение на переднем плане. Состояния загрузки и ошибки живут в `UiState` экрана фото. До завершения запроса ручное редактирование подписи этого фото недоступно. Успешный ответ сразу сохраняется как `caption` с источником `AI` (§6).
  При уходе приложения в фон, отзыве согласия или смене аккаунта клиент отменяет активный запрос. Для новой попытки пользователь снова нажимает кнопку.
- **Ошибки.** Без сети, при таймауте, отказе модели, лимите или отключённом ИИ экран показывает причину сбоя и действие «Повторить». Восстановление сети и перезапуск приложения сами по себе запрос не запускают.
- **Стоимость (ориентир на октябрь 2026, цены меняются — сверять с прайсом провайдера):**
  для недорогих моделей порядка $0.0002–0.002 за снимок. ИИ не главная статья расходов:
  хранение и трафик дороже.
- **Провайдер:** выбирается по доступности и оплате из России; смена провайдера затрагивает
  один класс на бэкенде (см. §14).

## 10. Бэкенд (черновик контракта)

Решает три задачи: аккаунты, хранение и синхронизация, прокси к ИИ.
Технология — открытый вопрос (свой сервис на NestJS или BaaS вроде Supabase/Firebase), см. §14.

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/auth/register` | Регистрация |
| POST | `/auth/login` | Вход → access + refresh |
| POST | `/auth/refresh` | Обновление токена |
| DELETE | `/account` | Удаление аккаунта и всех данных |
| PUT | `/places/{id}` | Создать / обновить место (идемпотентно по id) |
| DELETE | `/places/{id}` | Удалить место (tombstone) |
| POST | `/photos` | Загрузить фото: метаданные + файл (идемпотентно по id) |
| PATCH | `/photos/{id}` | Подпись и прочие поля |
| DELETE | `/photos/{id}` | Удалить |
| GET | `/sync?since=` | Изменения с курсора |
| POST | `/captions` | Сгенерировать подпись |

**`POST /captions` (черновик):**
- Запрос: `multipart/form-data` — `image` (JPEG) и `meta` (JSON: `photoId`, `placeName?`, `createdAt`, `language`).
- Ответ `200`: `{ "photoId": "...", "caption": "..." }`.
- Ошибки: `401` (нет сессии), `413` (файл слишком большой), `422` (невалидные данные),
  `429` (лимит), `503` (ИИ недоступен или выключен). Формат тела ошибки: `{ "code": "...", "message": "..." }`.

Детали контракта уточняются при старте работы над бэкендом.

## 11. Архитектура

**Clean + MVVM + UDF.** Зависимости слоёв направлены к домену (`:ui → :domain ← :data`).

```
:app      Android application: точка входа (Activity, Application) и сборка DI
:ui       Android library: Compose, ViewModel, тема и навигация
:domain   Kotlin/JVM: модели, интерфейсы репозиториев и сервисов, юзкейсы
:data     Android library: Room, сеть, воркеры WorkManager, реализации интерфейсов
```

`:app` подключает `:ui` и `:data` и связывает реализации с доменными контрактами через DI. Если код сборки
в `:app` использует доменные типы, `:app` объявляет прямую зависимость от `:domain`.
`:ui` и `:data` зависят от `:domain`. `:ui` получает данные через доменные контракты, а Entity, DTO и DAO
из `:data` недоступны при компиляции `:ui`. `:domain` компилируется без Android SDK и не зависит от других
модулей GeoGallery.

**Интерфейсы в `domain`:**
`PhotoRepository`, `PlaceRepository`, `AuthRepository`, `SettingsRepository`,
`CaptionGenerator`, `LocationProvider`, `PhotoSource` (камера сейчас, галерея в v2),
`SyncScheduler`; источник времени (`Clock`) и генератор id (`IdGenerator`) — тоже через интерфейсы,
чтобы тесты были детерминированными.

В MVP реализация `LocationProvider` в `:data` использует системный Android `LocationManager`.

**Стек (предварительно):** Kotlin, Jetpack Compose + Material 3, Navigation Compose (type-safe),
Coroutines + Flow, Room, WorkManager, CameraX, Hilt, kotlinx.serialization. Остальное — §14.

## 12. Приватность и безопасность

- Согласие на отправку фото в ИИ: отдельная настройка, по умолчанию выключена, отзываемая.
- В ИИ уходят только уменьшенные копии без EXIF и без точных координат.
- Бэкенд не хранит присланные для ИИ изображения дольше обработки запроса;
  условия провайдера по хранению и обучению на данных проверяются заранее.
- Токены хранятся в защищённом хранилище (DataStore + шифрование через Keystore; детали — на этапе аккаунтов).
- Ключи (ИИ, SDK карты, прочее) не лежат в репозитории и не зашиты в клиент без необходимости:
  ключ ИИ — только на сервере, ключ карты — через `local.properties` (в `.gitignore`).
- Приложение не читает галерею устройства (в MVP нет доступа к MediaStore).
- Удаление аккаунта удаляет данные полностью.
- Фото и геолокация — персональные данные. Для публичного релиза потребовались бы политика
  конфиденциальности и проверка требований законодательства (в том числе 152-ФЗ); пока публикации
  нет, достаточно честного описания в README.

## 13. Нефункциональные требования и состояния ошибок

Камера запрашивает разрешение при первом открытии с карты. Геолокация запрашивается при первом нажатии «Моё местоположение» или при первом снимке, если пользователь ещё не отвечал на запрос. Если доступ к геолокации уже выдан, карта и камера используют его сразу. Отказ в геолокации оставляет съёмку доступной и сохраняет фото без места.

- **Платформа:** minSdk 26; compile/target SDK — как в шаблоне Studio, обновляются по необходимости.
- **Производительность:** в сетку и на метки грузятся миниатюры, а не оригиналы; кэш изображений;
  плавная работа на 1000+ фото.
- **Надёжность:** снимок не теряется при потере сети или смерти процесса.
- **Тесты:** unit-тесты `domain` на JVM, ViewModel с fake-репозиториями, DAO (instrumented),
  по возможности один UI-тест.
- **Локали и тема:** ru и en (строки только в `strings.xml`), тёмная тема.

| Ситуация | Поведение |
|---|---|
| Нет разрешения на камеру | Экран с объяснением и кнопкой в настройки; просмотр архива работает |
| Нет разрешения на геолокацию / GPS выключен | Фото сохраняется без места; подсказка включить геолокацию |
| Координаты не получены за таймаут | То же: фото без места |
| Координаты получены, погрешность неизвестна или больше 30 м | Фото сохраняется с координатами и без места. Камера предлагает повторить замер через «Уточнить геолокацию» |
| Нет сети | Работа офлайн, статусы `PENDING`; действия «Требует сети» (ниже) показывают понятную ошибку, а не крутятся бесконечно |
| Нет сети, карта | Метки мест рисуются, тайлы — из кэша или пустой фон; список мест и все фото работают |
| Гостевой режим (нет аккаунта) | Всё работает локально; синхронизации и ИИ нет, индикаторы синхронизации скрыты |
| Токен истёк и не обновился | Локальные данные доступны, синхронизация на паузе; в настройках — «Войдите снова» |
| Архив пуст | Пустое состояние на карте с призывом сделать первый снимок |
| ИИ недоступен / лимит / отказ | «Подпись не получена» + «повторить»; фото не страдает |
| Нет места на диске | Сообщение, приложение не падает |
| Не загрузилась миниатюра | Placeholder |

**Требует сети** (без сети — сообщение и возможность повторить):
- регистрация и вход, включая перенос гостевых данных и первую загрузку данных аккаунта;
- удаление аккаунта;
- запрос подписи ИИ для выбранного фото;
- тайлы карты, которых нет в кэше.

Выход работает и без сети: после предупреждения о несинхронизированных данных локальный архив очищается.

## 14. Открытые вопросы

| Вопрос | Варианты | Решить |
|---|---|---|
| Бэкенд | Свой сервис на NestJS или BaaS (Supabase/Firebase) | Перед этапом аккаунтов |
| SDK карты | Yandex MapKit / MapLibre + OpenStreetMap / Google Maps (проверить доступность и ключи) | Перед этапом карты |
| Провайдер ИИ | Проверить доступность и оплату из России; интерфейс позволяет сменить | Перед этапом ИИ |
| HTTP-клиент | Retrofit или Ktor | Этап сети |
| Радиус места и порог погрешности | Стартовые значения 40 м и 30 м. Проверить на серии снимков в одной точке и в соседних местах | Этап геолокации |
| Судьба пустого места после удаления последнего фото | Правило из §5.3 или всегда оставлять | Этап просмотра фото |
| Конфликты синхронизации сложнее last-write-wins | Оставить как есть для MVP | Этап синхронизации |
| Хранение файлов на сервере | Объектное хранилище или БД/диск | Вместе с бэкендом |
| Загрузка изображений | Coil (предварительно) | Этап просмотра места и фото |
